# EqDiss on Kubernetes

These manifests run the current EqDiss code as finite Kubernetes Jobs. They are designed for reproducible scientific batch execution rather than for a long-running network service.

This configuration uses the EqDiss image, the repository's real shell entry points, a PersistentVolumeClaim for exported artifacts, non-root execution, explicit resource bounds, and a single-thread BLAS/OpenMP policy for method-to-method timing consistency.

## Prerequisite image

Build the image from the EqDiss repository root:

```bash
docker build --pull -f docker/Dockerfile -t REGISTRY/ediff:TAG .
docker push REGISTRY/ediff:TAG
```

Before applying a Job to a remote cluster, replace `ediff:latest` in the selected Job manifest with the immutable image tag or digest pushed to the registry. An immutable digest is preferable for archival experiments.

For local clusters such as kind or minikube, load the locally built `ediff:latest` image using the mechanism provided by that cluster, or push it to a registry visible to the nodes.

## Persistent results

`pvc.yaml` requests 20 GiB using the cluster's default StorageClass. The PVC stores exported result directories and execution metadata at `/artifacts` inside the container. The scientific code continues writing to its original paths under `/app`; the Docker entrypoint exports those paths after execution, so the research scripts are not modified for Kubernetes.

If the cluster has no default StorageClass, set `storageClassName` in `pvc.yaml` before applying it. If datasets must also be retained, change `EDIFF_ARCHIVE_DATASETS` from `"0"` to `"1"`; this can substantially increase storage consumption.

## Recommended sequence

First run the quick validation:

```bash
kubectl apply -f kubernetes/pvc.yaml
kubectl apply -f kubernetes/job-quick.yaml
kubectl wait --for=condition=complete --timeout=30m job/ediff-quick
kubectl logs job/ediff-quick
```

Delete the completed quick Job before rerunning it:

```bash
kubectl delete job ediff-quick
```

Run the main extended experiment:

```bash
kubectl apply -f kubernetes/job.yaml
kubectl wait --for=condition=complete --timeout=12h job/ediff-extended
kubectl logs job/ediff-extended
```

Run the SOTA and SDP validation separately:

```bash
kubectl apply -f kubernetes/job-sota.yaml
kubectl wait --for=condition=complete --timeout=24h job/ediff-sota
kubectl logs job/ediff-sota
```

`kustomization.yaml` intentionally contains only `pvc.yaml` and the main extended `job.yaml`, so `kubectl apply -k kubernetes` does not accidentally launch all three workloads.

## Retrieve artifacts

The results survive Pod termination because they are copied to the PVC. A portable way to inspect or copy them is to mount the same claim in a temporary Pod:

```bash
kubectl run ediff-artifact-reader --rm -it --restart=Never \
  --image=busybox:1.37 \
  --overrides='{"spec":{"containers":[{"name":"ediff-artifact-reader","image":"busybox:1.37","command":["sh"],"stdin":true,"tty":true,"volumeMounts":[{"name":"artifacts","mountPath":"/artifacts"}]}],"volumes":[{"name":"artifacts","persistentVolumeClaim":{"claimName":"ediff-artifacts"}}]}}'
```

Inside the temporary Pod, inspect `/artifacts`. The directory contains `container_execution.txt`, `exit_code.txt`, and every result tree generated by the selected workflow.

## Scientific execution modes

The manifests correspond directly to the repository commands:

- `job-quick.yaml`: `bash run_quick.sh --regenerate-datasets --seeds 11`
- `job.yaml`: `bash run_extended.sh --regenerate-datasets --seeds 11,17,23,31,37,43,53,61`
- `job-sota.yaml`: `bash sota.sh --regenerate-datasets --seeds 11,17,23,31,37,43,53,61`

To reproduce another seed set, change only the value following `--seeds`. To retain existing generated datasets within a single container execution, omit `--regenerate-datasets`; note that each Kubernetes Job starts with a fresh container filesystem unless datasets are explicitly persisted and restored.

## Resource policy

The quick Job requests 1 CPU and 2 GiB; the extended Job requests 2 CPUs and 4 GiB; the SOTA Job requests 4 CPUs and 8 GiB. Limits are intentionally higher to accommodate optimization routines. These values are operational defaults, not mathematical requirements. If a cluster enforces different quotas, adjust requests and limits without changing the scientific command.

For timing comparisons, all methods must run under equivalent resources. The manifests therefore set `OMP_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`, and `MKL_NUM_THREADS=1`. Use the same node architecture and preferably the same node pool for every compared method. Kubernetes scheduling, CPU throttling, noisy neighbors, and heterogeneous processors can materially alter elapsed-time measurements even when the algorithms and image are identical.

## Security properties

The Pod and image run as UID/GID 10001, disallow privilege escalation, drop Linux capabilities, and request the runtime-default seccomp profile. No Service, ingress rule, host networking, privileged container, hostPath mount, or cluster-wide RBAC permission is required.

## Failure handling

`backoffLimit: 0` prevents Kubernetes from silently repeating a failed scientific run. The entrypoint records the command exit status and copies any result directories already produced to the artifact PVC. Inspect both Kubernetes logs and `/artifacts/exit_code.txt` when a Job fails.

Because Jobs have stable names, Kubernetes will not rerun a completed Job merely by reapplying the same YAML. Delete the old Job first, then apply the manifest again. Keep the PVC if the prior artifacts must be preserved externally; the entrypoint replaces result directories of the same name on each run.
